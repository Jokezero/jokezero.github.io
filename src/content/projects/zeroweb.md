这是本站本身。它既是一个能长期写下去的博客，也是一次完整工程实践的记录 ——
从空目录到上线，再到上线后一轮又一轮地修 bug。

下面按"为什么这么做 → 怎么做的 → 踩了什么坑"三层来写，方便你要么复刻，要么避坑。

---

## 一、先把约束钉死，再谈选型

动手之前先写下三条不可动摇的约束，后面所有取舍都拿它们当尺子：

1. **部署在 GitHub**，纯静态托管，**没有后端服务**。
2. **尽可能轻**，首屏要快；动效必须能降级，绝不能拖慢加载。
3. **要有硬核科技感、允许炫技**，但不许以牺牲可读性、可访问性和性能为代价。

外加一条长期约束：**必须能长期维护** —— 依赖尽量少、内容与代码分离、
关键决策有记录、质量有自动化门禁。

第四条最容易被忽略，却最影响"两年后还能不能继续写"。
一个三个月后就没人敢改的个人站，本质上和没做过一样。

## 二、选型：把复杂度都留在构建期

| 层   | 选型                             | 理由                                                         |
| ---- | -------------------------------- | ------------------------------------------------------------ |
| 框架 | Astro（全静态预渲染）+ TypeScript | 产物是纯 HTML/CSS/JS，没有服务端要运维                        |
| 样式 | Tailwind v4 + 设计令牌            | 颜色/字号/间距集中在 `src/styles/tokens.css` 一个文件          |
| 内容 | Markdown + 内容集合（zod 校验）   | 发文章 = 加一个 `.md`；字段写错在构建期报错，而不是线上白屏   |
| 视觉 | Canvas 2D 实时模拟                | 首页三体运动、文章页原子、项目页线框球、关于页双摆            |
| 搜索 | Pagefind                          | 索引在构建期生成，运行时零第三方请求                          |
| 评论 | giscus（默认关闭）                | 需要时填四个 ID 即可开启，不需要就完全不加载                  |
| 门禁 | GitHub Actions                    | 部署 + 质量检查（类型 / 格式 / 体积 / 死链 / Lighthouse）     |

一个贯穿始终的判断：**能在构建期做完的事，绝不留给运行时。**
搜索索引、图片多尺寸、分享卡片、GitHub 数据都是构建期产物，访客拿到的就是最终文件。

## 三、分阶段施工：P0 → P5

整个过程切成六个可独立验收的阶段，每阶段做完先停下来验收，再进下一步。
这一步的价值在第四节会体现得非常明显 —— **出问题时你能知道是哪一层的锅**。

### P0 · 打通部署链路

目标只有一个：**空站点能自动部署上线**。

先做一条最短闭环 —— 推送 → 自动构建 → 发布到 GitHub Pages，哪怕页面只有一行字。
链路不通，后面写多少功能都是悬空的。

顺带定下几个约定：手写工程骨架而不用交互式脚手架（依赖少、每一项都知道来历）、
锁定 Node 与 pnpm 版本、依赖的构建脚本走白名单。

### P1 · 设计系统与骨架

把视觉规范翻译成代码里可复用的东西：设计令牌（颜色 / 字号阶梯 / 间距 / 动效时长）、
顶栏与页脚、主题切换、404 页、自托管字体。

主题切换这里埋了一个坑：**切换不能闪**。做法是让 `data-theme` 成为唯一状态来源，
并在 `<head>` 里放一段约 200 字节的**同步内联脚本**，排在样式表之前执行 ——
先读本地存储，没有就跟随系统偏好，兜底深色。脚本先于样式，所以不可能出现"先白后黑"。

另外，亮色主题**不是颜色反转**。同一套变量名在亮色下重新校准过灰度：
次要文字在白底上从 0.52 提到 0.6 —— 因为 0.52 在白底只有 4.27:1，够不到正文 4.5:1 的红线。

### P2 · 内容系统

文章、项目、标签、关于、全文搜索、RSS 全文。

核心设计是**内容与代码分离**：所有字段都过 zod 校验，写错在构建期直接报错。
发一篇文章就是加一个 Markdown 文件，不用碰任何组件代码。

搜索用了 Pagefind，但第一天就发现它的默认行为有问题：**它会把整份 HTML 都索引进去**。
于是幕布上的 `LOADING`、跳转链接、顶栏导航、页脚社交链接全变成了可被搜到的"词条" ——
搜索框里敲一个 `l`，会冒出一堆 `LOADING.xxx` 这种对访客毫无意义的噪声。

修法是给它划定范围，**只索引正文**。这条经验适用于任何全文搜索：
默认全文，不等于全部值得搜。

### P3 · 招牌视觉

四套 Canvas 背景模拟 + 页面切换动效 + 滚动特效 + 首次进入的字符绘制。

背景都是纯装饰，所以做了完整的降级链路：减少动态效果偏好、省流量模式，
以及三个"保险丝"开关 —— 改一个值就整体回退，不用动任何逻辑：

```ts
features.heroEffect = "static";   // 关掉四套实时背景，回到纯黑
features.pageTransition = false;  // 关掉页面切换幕布
features.introArt = false;        // 关掉首次进入的字符绘制
```

而这个阶段做出来的页面切换动效，就是下一节全部故事的起点。

### P4 · 质量门禁

让"改坏了"这件事在合并之前就被拦住，而不是靠人记得去检查：

```bash
pnpm verify   # 类型 + 格式 + Lint + 构建 + 体积预算 + 死链
```

体积预算是硬性红线，超了直接失败：

| 项目             | 预算   | 实测          |
| ---------------- | ------ | ------------- |
| 首屏 HTML（首页） | 25 KB  | 6.22 KB gzip  |
| 全站 CSS 合计     | 30 KB  | 8.96 KB gzip  |
| 全站 JS 合计      | 40 KB  | 10.42 KB gzip |
| 自托管字体        | 120 KB | 43.08 KB gzip |

Lighthouse 也设了断言：性能 ≥ 0.9、可访问性 ≥ 0.95、最大内容绘制 ≤ 2.5s、布局偏移 ≤ 0.05。

**门禁立刻就抓到东西了**：可访问性检查一直失败，原因是"微标签"的灰色对比度不够，
过不了对比度这一项。把灰度提到 4.92:1 才通过。
如果没有门禁，这个瑕疵会一直留在线上，而且肉眼几乎看不出来。

### P5 · 维护机制

最后一步不是加功能，而是保证**半年后的自己还愿意回来改**：

维护手册（本地启动 / 发文章 / 改视觉 / 部署，四条可复制的操作路径）、
维护日历（每周处理依赖更新、每月看一次体积与跑分、每季度完整跑一次门禁）、
每日定时重建（刷新构建期抓取的 GitHub 数据）、依赖更新机器人自动提 PR。

还有一条处理"文档没写到的取舍"的规则：**先按推荐默认值做，然后补一条 ADR**；
改主意时不要修改历史记录，新写一条并标注"取代 00XX"。
整站记了 19 条 ADR，这份记录在后面的调试里出了大力。

## 四、一场和"闪一下"的持久战

上线之后，真实的 bug 才开始。最典型的是**切换页面时整个网页闪一下，露出浏览器的底色**。

这个 bug 前后修了五轮，每一轮都把认知往前推一层，很值得完整记下来。

### 第 1 轮：三个独立的实现缺陷

现象是"切换页面时**有时不播动效**，而且**动效结束后幕布又出现了一次**"。

拆开看是三个独立问题：

1. **到达页没有注册点击拦截**。早期版本在"到达分支"里直接返回了，
   于是从刚跳过去的页面再点导航就退化成普通跳转 —— 表现为动效"一次播、一次不播"。
2. **收尾时复位幕布，被看见了**。动画结束时解除了遮盖状态，幕布于是带着过渡从视口下方
   **动画回到上方**，正好穿过整个画面 —— 这就是"动效结束后幕布又出现"。
   改成：收尾只解除"切换中"标记，幕布停在视口下方；复位只在下一次切换开始时、
   且带着"不要动画"的类完成，永远发生在画面之外。
3. **首帧覆盖不能交给 JS**。注释里写着"CSS 保证首帧幕布盖满画面"，
   但那条规则当时**根本没写**。脚本被外置成独立文件后，执行时机可能晚于首次绘制，
   于是会先闪一下新页面。

### 第 2 轮：把 transition 换成 animation

修完第一轮，又发现"第一次进入某页面正常，**再次**进入同一页面时还是会闪"。

根因是同一个坑的第二种表现：**幕布原本用 CSS transition 做位移**。
transition 只有在"起始状态已经被浏览器提交过"时才会播放；
而"加类"和"新文档首次绘制"经常落在同一帧 —— 资源全命中缓存时，
脚本跑得比首次绘制还早，于是"盖满画面"这一帧从未被提交，
揭开那一下被整帧跳过，新页面就硬生生地出现了。

**改成关键帧动画**（动画永远从第一帧开始播，不依赖初始状态是否被提交）之后，
连续三次进入同一页面，幕布位移曲线完全一致。

> **教训（同类问题在本项目出现过三次）**：只要"元素出现"与"状态切换"可能发生在同一帧，
> 就用 **animation** 而不是 **transition**。幕布揭开、逐字显影、开机遮罩，全栽在这一条上。

### 第 3 轮：一次对照实验定位到了根因

问题依然存在。于是有了整个项目里最关键的一次定位：

> 把浏览器背景色设成白色、网页是黑底时，那一闪**极其刺眼**；
> 把浏览器背景设成黑色，几乎看不见。

再加上一条时间线证据：幕布上的进度条走到**最后 1/10** 时页面闪一下 ——
进度条是 760ms 的动画，90% 大约是 800ms，正好对应跳转后约 260ms 那一刻。

结论一下清晰了：**闪的那一帧不在文档里面，而在两份文档之间。**
浏览器在"旧文档已丢弃、新文档还没画出来"的瞬间会铺自己的底色，Firefox 默认是白色。

之前几轮修的全是**文档内部**的问题（黑色遮罩、把幕布挪到 body 首位、内联关键样式、
动画填充模式），而这个空档在文档外面，幕布再厚也盖不住它。

唯一能盖住跨文档空档的机制是跨文档视图过渡，但实测浏览器不支持：

```js
CSS.supports("@view-transition { navigation: auto; }"); // false
```

这条路走不通。

### 第 4 轮：换掉架构，而不是继续打补丁

既然"文档之间"这个空档是**多页架构本身**带来的，那就消灭多页跳转本身 ——
**站内导航改成不换文档的 SPA 式切换**：

```text
点击 → 幕布下扫（520ms，同时并行预取新页面）
     → 在幕布完全覆盖期间把新页面内容搬进当前文档
     → 重新挂载该页行为 → 幕布落下（560ms）
```

关键设计有九条，其中最重要的三条：

1. **唯一客户端入口**。所有页面行为拆成可重复挂载的初始化函数，换页后统一重新挂载；
   需要收尾的（全局监听、观察器、动画循环）返回销毁函数，换页前统一调用。
2. **常驻层跨页面存活**。幕布、开机遮罩、滚动进度线在换页时**原地不动**，
   只替换其余节点 —— 幕布因此永远待在同一份文档里，结构上不可能再出现"文档之间"的空档。
3. **时序不再依赖加载速度**。内容替换发生在幕布完全覆盖期间，
   所以"新页面多快加载完"完全不影响观感（顺带修掉了"第二次进入同一页动效变短"）。

动手之前先做了备份（git 标签 + 完整快照），这样后面发现回归随时能比对、能回退。
**重构之前先留退路，是这一轮最省时间的决定。**

### 第 5 轮：重构带来的新问题，以及"逐项对比"验收

架构换完，果然冒出一批新问题：

1. **动效被连续触发两次**。根因是重构时把常驻层**摘下来又插回去** ——
   重新插入 DOM 会让元素身上的 CSS 动画**从头再播一遍**。
   改成"只替换其余节点"后，一次点击的幕布轨迹只有一个方向变化。
2. **手机上关于页滚不到页脚**。强制滚动吸附会把滚动死死拽回分节起点，
   最末一节之后的页脚**永远看不到**，手指滑动还被反复弹回。
   改成：桌面保留强制吸附（这是"一屏一节"那股干脆手感的来源），触屏上完全关掉。
3. **右下角的分节计数压住页脚**。页脚进入视口时隐藏计数。
4. **首屏标题不再渐隐、而是一滚就没**。滚动特效脚本在初始化时缓存了首屏元素的引用，
   换页后那个节点已被替换，读到的高度是 0，透明度瞬间归零。
   改成每次读取滚动量都重新查一次元素。

> 第 4 条和第 1 条其实是同一类错误：**缓存了会跨"换页"失效的引用**。
> 在任何"内容会被替换"的架构里，缓存 DOM 引用都是定时炸弹。

最后做了一次**逐项对比验收**：把重构前那一版构造成对照站点，
用同一套测量脚本在 390 / 1280 两个宽度、6 个页面上逐项比对 ——
顶栏高度、导航显示状态、正文首个元素位置、页脚位置、页脚两栏文案、滚动吸附类型，
**全部一致**，唯一差异是版本号本身（因为提交数变了）。

重构类改动的验收标准应该是"**行为等价**"，而不是"看起来没坏"。

## 五、其他几个值得记的坑

**页脚版本号**。原型里写死了 `REV 27`，而手写的序号一定会忘记递增。
改成由 git 历史自动计算：`v2026.09.3.5` 表示 2026 年 9 月的第 3 次功能更新、
第 5 次修复与维护，按提交前缀分类计数、每月归零。
好处是**不可能忘记递增**，而且可复现。
代价是持续集成里必须显式拉取完整历史（默认只取 1 个提交，计数器会永远是 0）。

**404 页的"伪终端"**。为了气氛写了 `$ cat /dev/requested-path` 这种伪造命令，
但对访客来说它只会造成困惑。**装饰性文案不能冒充真实信息**，删掉。

**开发者文案泄漏到线上**。搜索页曾经写着"索引在构建期生成；本地开发环境下不可用" ——
这是写给开发者看的，不该给访客看。上线后专门做了一轮"扫一遍所有面向用户的文案"。

## 六、沉淀下来的几条通用经验

1. **元素出现 + 状态切换可能同帧 → 用 animation，不用 transition。** 这一条踩了三次。
2. **重新插入 DOM 会重播 CSS 动画。** 需要跨"内容替换"存活的元素，就让它原地不动。
3. **不要跨换页缓存 DOM 引用。** 每次用之前重新查询，成本可以忽略，bug 少一大类。
4. **改浏览器背景色是最快的定位手段之一。** 白底黑页那一闪，直接把问题从"文档内"逼到"文档之间"。
5. **能盖住跨文档空档的只有跨文档机制。** 如果浏览器不支持，唯一的出路是把"跨文档"从架构里拿掉。
6. **重构之前先留退路**，重构之后用"逐项行为对比"验收，而不是凭感觉。
7. **拿不准的取舍要写下来。** ADR 的作用是让你能分清"当初为什么这样"和"现在坏了"。
8. **让机器记住规则。** 类型检查、体积预算、对比度门禁、死链检查 —— 凡是"人一定会忘"的事，都交给持续集成。
9. **面向用户的文案要单独过一遍。** 开发者的自我说明很容易顺着模板漏到线上。

## 七、最终形态

- **规模**：26 次提交、19 条决策记录、7 份设计文档、约 5800 行源码。
- **体积**：全站 JS 10.42 KB gzip（预算 40 KB）、CSS 8.96 KB（预算 30 KB）、
  首屏 HTML 6.22 KB（预算 25 KB）、字体 43.08 KB（预算 120 KB）。
- **门禁**：每次推送自动跑类型 / 格式 / 检查 / 构建 / 体积 / 死链；Lighthouse 四项断言。
- **部署**：推送即上线，另有每日定时重建用于刷新动态数据。

最满意的一点不是动效，而是**这个站现在是可以被继续改下去的**：
内容与代码分离、关键决策有记录、质量有门禁、视觉参数集中在令牌文件里、
三个开关能让炫技部分一键降级。

毕竟个人网站真正的失败方式，从来不是做得不够漂亮，而是做完就再也没打开过。
