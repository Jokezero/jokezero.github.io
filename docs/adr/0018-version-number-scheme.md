# 0018 · 站点版本号的格式与算法

状态：已采纳（2026-09-30，P5 之后）

## 背景

页脚原来只有一行 `Build 2026-09-30`（构建日期）。构建日期说明不了"这是第几次更新"，
而个人站最需要的一个信号恰恰是"这个站还在被维护"（`03-open-questions.md` A13）。
设计原型里用的是手写 `REV 27 · 2026-09-29`，但手写的序号一定会忘记递增。

站点主人提出的规则：**年.月.第几次大更新.第几次小更新**，要求清晰易读。

## 决策

页脚右下角显示：

```
v2026.09.3.5 · Build 2026-09-30
 │   │  │ └── 当月第 5 次修复与维护（fix / docs / chore / test / style…）
 │   │  └──── 当月第 3 次功能更新（提交信息以 feat 开头）
 │   └─────── 月份
 └─────────── 年份
```

### 由 git 历史自动计算，不手工维护

`src/lib/version.ts` 在构建期执行 `git log --since=<当月 1 日> --pretty=%s`，
按提交信息前缀分类计数：

| 提交前缀 | 计入 |
| --- | --- |
| `feat:` / `feat(scope):` / `feat!:` | 功能更新（第 3 位） |
| 其他（`fix` / `docs` / `chore` / `test` / `style`…） | 修复与维护（第 4 位） |

这样定义的三个好处：

1. **不可能忘记递增** —— 版本号就是历史，写多少就是多少；
2. **可复现** —— 同一次提交重复构建，版本号完全一致；
3. **和提交习惯一致** —— 仓库一直用 `feat(p2): …` / `fix(footer): …` 这种前缀，不需要额外流程。

### 两个使用上的约定

- **按自然月重置**：计数器只统计当月，所以 10 月 1 日会从 `v2026.10.0.0` 重新开始。
- **每日定时重建不会改变版本号**（它不产生提交），只有页脚里的 `Build` 日期会变 ——
  正好区分了"有新东西"和"只是刷新了数据"。

### 为什么 CI 里要 `fetch-depth: 0`

`actions/checkout` 默认只取 1 个提交，那样计数器永远是 0。
所以 `deploy.yml` 与 `quality.yml` 都显式设了 `fetch-depth: 0`（仓库很小，代价可忽略）。
取不到历史时（浅克隆、从压缩包构建）版本号退化为 `v<年>.<月>.0.0`，构建不会失败。

## 影响

- 页脚一行就同时表达了"维护频率"与"最近构建时间"，不需要任何手工维护成本。
- 想改规则（例如把 `feat` 换成别的判定、或改成按周重置），只改
  `src/lib/version.ts` 的 `FEATURE_PATTERN` 与 `--since` 参数，其余不用动。
- 页脚那一行带 `title` 提示，鼠标悬停会显示"版本号：年.月.当月功能更新次数.当月修复与维护次数"。
