# 后端 / 数据层设计（下一阶段）

> 前置事实：站点部署在 **GitHub Pages**，它是纯静态托管——**没有服务器进程、没有数据库、不能接收表单、不能保存任何东西**。
> 所以"后端设计"在本项目里的真实含义是：**哪些能力用构建期解决、哪些用第三方静态服务解决、哪些真的需要一台服务器**。
> 本文档给出选型框架与决策清单（对应 `03-open-questions.md` 的 C 组，但更细）。

---

## 1. 三种"后端"路线（先选路线，再谈细节）

### 1.0 已确认的四条需求（2026-09-29）与对应结论

| 你的需求 | 结论 |
| --- | --- |
| 能很方便地更新 / 上传内容 | **内容一律是 Markdown**；发布 = 在 **GitHub 网页上直接编辑并提交**，不需要本地环境、不需要装任何东西。进阶可用在线编辑器（在仓库页按 `.` 打开）或 Codespaces。 |
| 网站易于维护与更改 | 依赖最小化 + 内容与代码分离 + 门禁自动化（体积/可访问性/死链），细节见 `01-design-spec.md` §10。 |
| 部署在 GitHub、访问要快 | **路线 A（纯静态）**，GitHub Pages + 其全球 CDN；继续守住首屏体积预算。 |
| 站内要有外链（项目页指向对应 GitHub 仓库） | 项目条目增加 `repo` 字段，构建期渲染成外链；需要 star 数则在**构建期抓取**，不调客户端 API。 |

> **因此 G1 = A（纯静态）**。下面 G2–G11 按此前提选择。

### 1.1 内容更新：三档便利度，按需升级

| 档位 | 做法 | 门槛 | 适用 |
| --- | --- | --- | --- |
| **① 网页编辑（默认）** | 在 GitHub 打开 `src/content/posts/xxx.md` → 编辑 → Commit。新增文章用仓库模板复制一份改名即可；插图直接在编辑框里拖拽上传 | 会用浏览器 | 绝大多数更新 |
| ② 在线 IDE | 在仓库页按 `.` 打开 github.dev，或开 Codespaces，有语法高亮与实时预览 | 略懂目录结构 | 一次改多篇、调整结构 |
| ③ 图形化后台 | 加 **Decap CMS**（页面里内置的管理界面，提交仍是 Git 提交） | 需额外配一个 OAuth 代理（属于路线 B 的一小块 Serverless） | 完全不碰文件、纯表单式写作 |

**默认按 ① 走**，②随时可用；等真觉得"连文件名都不想碰"时再上 ③。

保证 ① 不出错的三个前提（实现时必须做）：
1. frontmatter 用 zod 校验，字段写错**在构建期就报错**并阻止部署，不会把坏页面推上线；
2. `pnpm new:post` 脚本生成带正确字段的模板，且仓库里保留一份可直接复制的示例；
3. CI 会检查死链与图片路径，写错链接时构建失败而不是静默 404。

### 1.2 项目条目的数据模型（含 GitHub 外链）

```yaml
# src/content/projects/<slug>.md
title: 分布式日志聚合管道
summary: 把 40 台机器的日志收敛进一条管道，端到端延迟 800ms。
stack: [rust, kafka]
year: 2025
repo: https://github.com/<user>/<repo>     # 必填：指向对应仓库
demo: https://…                            # 可选：在线演示
featured: true                             # 可选：是否进首页精选
```

- 外链一律 `target="_blank"` + `rel="noopener noreferrer"`；用 `<a>` 承载，键盘与屏幕阅读器可用。
- 需要展示 star 数时：GitHub Actions 在构建期用只读 `GITHUB_TOKEN` 抓取 → 写入 JSON → 前端读静态文件；**不要在浏览器里调 api.github.com**（速率限制 + 额外请求 + 暴露来源）。
- 项目页现有的左侧控制栏（搜索 / 技术栈 / 页码 / 每页数量）直接复用这套字段：技术栈筛选来自 `stack`，搜索匹配 `title + summary`。

| 路线 | 说明 | 成本 | 适合 |
| --- | --- | --- | --- |
| **A·纯静态（推荐起点）** | 所有数据在构建期写进产物：内容来自 Markdown、动态数据由 GitHub Actions 定时抓取、评论/统计用第三方托管服务 | 0 元 | 个人博客/自我介绍，长期维护，不想运维 |
| **B·静态 + 云函数** | 在 A 之上加少量 Serverless（Cloudflare Workers / Vercel Functions）：真实表单提交、动态接口、简单鉴权 | 0–20 元/月 | 需要"能写进数据库"的功能（联系表单、点赞、访问统计自建） |
| **C·自建服务** | 一台 VPS + 数据库 + 自建 Umami/giscus 后端 | 30–80 元/月，需要运维 | 想要完全掌控数据、或用后端能力本身作为展示 |

**建议**：先走 A，把站点跑起来；把"需要 B 才能做的功能"列成待办，等真正需要时再加。避免为了一个联系表单就上 VPS。

## 2. 能力清单：每项在静态站里怎么落地

| 能力 | 推荐方案 | 关键约束 |
| --- | --- | --- |
| 内容存储 | **Markdown + MDX 进 Git**（已经是既定方案） | 内容即数据，天然有版本历史与多副本备份 |
| 发布流程 | 写文件 → 推送 → Actions 构建 → Pages 部署 | 全流程可回滚；草稿用 frontmatter `draft` |
| 计划发布 | GitHub Actions 每日定时重建（`schedule`） | 构建期按 `pubDate` 过滤未来文章 |
| 动态数据（GitHub star 数、贡献图） | **构建期抓取**写入 JSON，前端只读静态文件 | 用只读 `GITHUB_TOKEN`，避免客户端 API 限流 |
| 评论 | **giscus**（GitHub Discussions） | 需开启 Discussions；懒加载（滚动到评论区才加载） |
| 站内搜索 | **Pagefind**：构建期生成索引 | 索引分片按需加载，首屏零成本 |
| 访问统计 | Umami Cloud / Cloudflare Web Analytics / GoatCounter（三选一） | 隐私友好、≤3 KB 脚本、无 Cookie 横幅 |
| 图片处理 | 构建期 `astro:assets` + sharp 输出 AVIF/WebP 多尺寸 | 仓库里只存原图，产物里是优化后的图 |
| 联系表单 | 首版用 `mailto:`；需要真表单走 **Web3Forms / Cloudflare Worker** | 静态站无法接收 POST；表单必然涉及第三方 |
| RSS / Sitemap / OG 图 | 构建期生成 | 无服务端依赖 |
| 邮件订阅 | 第三方（Buttondown / Follow It）或干脆只提供 RSS | 自建订阅要处理退信与合规，成本高 |
| 访问控制 / 私密内容 | **不要在静态站做**（前端代码人人都能看） | 真有需求只能走 B/C 路线 |

## 3. 安全与密钥（最容易出错的地方）

1. **任何密钥都不能进前端**。构建期使用的 token 只放 GitHub Actions Secrets。
2. GitHub API 只用只读、最小权限的 `GITHUB_TOKEN`；不要用个人 PAT 长期挂在 CI 里。
3. 第三方脚本（评论、统计）一律**懒加载**，并在设计文档里登记体积与来源。
4. 依赖治理：Dependabot 每周提 PR，只有 CI 全绿才合并；`pnpm audit` 定期看。
5. 若引入 Serverless：所有对外接口都要有**限流**（免费额度被刷爆是常见事故），并把密钥放环境变量。

## 4. 需要你确认的决策（C 组细化）

每项都给推荐值，可以直接答"按推荐"。

| # | 问题 | 推荐默认 | 影响 |
| --- | --- | --- | --- |
| G1 | 路线选 A / B / C？ | **A 纯静态** | 决定运维成本与可行功能边界 |
| G2 | 评论：要 / 不要？ | **要**，giscus | 需开启仓库 Discussions，涉及第三方脚本 |
| G3 | 搜索：要 / 不要？ | **要**，Pagefind | 几乎零成本，强烈推荐 |
| G4 | 统计：要 / 不要？选哪个？ | **要**。只看流量概览 → **Cloudflare Web Analytics**（无限量、脚本 ~1 KB）；还想统计"项目页外链被点了几次"这类事件 → **Umami Cloud**（支持自定义事件与外链点击） | 两者都无 Cookie、无需同意横幅；真正的差别是**数据能力**，以及是否能自建（自建属于路线 C） |
| G12 | RSS 输出全文还是摘要？ | **全文** | 全文＝读者在阅读器里直接读完，站内访问量略低；摘要＝必须点进站，流量更高但阅读体验差一些。RSS 不占首屏性能 |
| G5 | 是否需要联系表单（而非 mailto）？ | 首版不需要 | 需要则走 B 路线或第三方服务 |
| G6 | 是否需要邮件订阅？ | 不需要，只提供 RSS | 订阅服务有成本与合规负担 |
| G7 | 是否展示 GitHub 动态数据？ | 需要（star 数、最近提交） | 用构建期抓取，每日定时重建 |
| G8 | 仓库公开还是私有？（Pages 部署公开站点通常需公开仓库，私有需付费计划） | 公开 | 影响评论（Discussions）与 Actions 配额 |
| G9 | 是否需要英文版 / 多语言？ | 暂不需要，结构预留 | 影响内容模型与路由 |
| G10 | 数据可迁移性要求？（未来换框架/平台） | 高：内容只用 Markdown + 标准 frontmatter | 避免锁死在某个 CMS |
| G11 | 是否需要"以后接 CMS"（如 Decap/Sanity）？ | 暂不需要；保持 Markdown 可迁移即可 | 接 CMS 会增加依赖与维护面 |

### 4.1 已确认（2026-09-29）

| # | 结论 | 备注 |
| --- | --- | --- |
| G2 | **要评论，用 giscus** | **不需要自建账号体系**：评论者用他们自己的 GitHub 账号，评论存在仓库 Discussions；你不需要数据库、不需要处理密码。安全模型不变（详见 `06-content-model.md` §1） |
| G6 | 不做邮件订阅 | 只提供 RSS |
| G7 | 文章与项目都要支持**图片**；项目还要支持 **GitHub / B站等外链与视频链接** | 图片在构建期优化；外链统一 `target="_blank" rel="noopener noreferrer"` |
| G8 | 不需要置顶、不需要计划发布 | 定时重建工作流仅用于刷新 GitHub 动态数据（可选） |
| 新增 | **多标签同时筛选**（文章页与项目页） | **已确认：OR 筛选 + 按匹配度排序**（命中标签多的排前，并列按日期倒序）；原型目前仍是单选，需按 `06-content-model.md` §4 改造 |

## 5. 建议的执行顺序（后端部分）

1. **定路线**（G1）→ 决定后面所有选择。
2. **打通内容管道**：Collections → 列表页 → 详情页 → RSS/Sitemap（这部分与前端实现并行）。
3. **接静态服务**：搜索 → 评论 → 统计，逐个接入并在 `01-design-spec.md` 登记体积与来源。
4. **加自动化**：每日定时重建（动态数据 + 计划发布）、Dependabot、质量门禁。
5. **最后才考虑 B 路线**：只有在出现"必须写入数据"的真实需求时，才引入 Serverless。

> 每一步完成后都要回到 `02-build-and-deploy.md` 的验收清单核对一遍，尤其是**首屏体积预算**——第三方脚本是最容易把轻量目标悄悄破坏掉的地方。
